## 1. Summary

Admins now have a moderation queue over every rating. Until now ratings could only be read one target at a time, through the public cursor list, which shows the reviewer's name and nothing else. The admin list shows who wrote each rating (id, email, account state) and can filter to "has a comment" and "low score", the combination a moderator actually needs.

This task is **read-only**. Deleting a rating or clearing its comment is Open Item **B3**: `Rating` has no `deletedAt`, so a delete would be permanent and would change every rating summary it counted towards.

## 2. Endpoint

| Method | Path | Returns | Errors |
|---|---|---|---|
| GET | `/admin/ratings` | Every rating, newest first, as `{ data, meta }`, **page-based**. Filters: `targetType?`, `targetId?`, `userId?` (the reviewer), `hasComment?`, `maxScore?` (1–5, inclusive), `page`, `limit`. Each row: `id, targetType, targetId, score, comment, orderId, createdAt, updatedAt, user { id, name, email, isActive }`. | 400 on a bad enum, uuid or boolean, an out-of-range score, or an unknown query field (for example `cursor`) |

- **`hasComment` treats `''` as no comment.** `true` means non-null and non-empty; `false` means null or empty. There's an e2e fixture for exactly this case.
- **Page-based, not keyset**, which matches every other admin list. The public `GET /social/ratings` keeps its cursor.
- There's no `GET /admin/ratings/:id`. The spec (A6) only asks for the list, and a list row already has every column.
- Class-level `JwtAuthGuard` and `RolesGuard` with `@Roles(Role.ADMIN)`. It's a read, so there's no audit. One `$transaction([count, findMany])` with the reviewer in the same `select`, so there's no N+1.

## 5. Findings

They fail **when the suite runs alone too**, so this isn't interference from other suites. The fixture creates its vendor without `verified: true` and its product with the default `approvalStatus: PENDING`. Since `6fd94ef` ("follow/favorite target validation", fix.js VULN-04), favorites and follows need a **publicly visible** target, so both return `404 TARGET_NOT_FOUND`. The API is behaving correctly and the fixture is stale. The fix is to seed `verified: true` on the vendor and `approvalStatus: 'APPROVED'` on the product in that suite's `beforeAll`. **This diff doesn't touch favorites or follows**: the only changes to `social.service.ts` are a new admin method and an import.

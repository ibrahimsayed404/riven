## 5. Contract changes the dashboards must absorb

All documented in `specs/web-dashboard-endpoints.md` §5a/§5b and §6.

1. **Errors** are `{ code, message, details? }` — no `{ success:false, error }` envelope.
2. **Every list** returns `{ data, meta: { total, page, limit, totalPages } }`; `?page` ≥ 1, `?limit` 1–100; unknown enum filters are `400`, not `500`.
3. **`PATCH /orders/:id/cancel`** cancels the whole checkout group and returns `cancelledOrderIds`.
4. **Vendor `category`** is an enum (`FASHION | FOOD | HOME_CRAFTS | BEAUTY | ACCESSORIES | KIDS | ART | OTHER`) on register, profile and search.
5. **Ratings:** `orderId` optional; required for VENDOR/PRODUCT, absent for BAZAAR.
6. **`POST /auth/register`** creates SHOPPER only; `role` may be omitted or `SHOPPER`.
7. **Rate limits:** 300/min per user (per IP anonymous), 10/min on login/register, 1/min on location updates → `429 RATE_LIMITED` + `Retry-After`.
8. **CORS** allow-list from `CORS_ORIGINS` (defaults to localhost:3000/3001).
9. **Public reads** (`GET /vendors/:id`, `GET /products/:id`) no longer include `ownerId`, `subscriptionStatus`, `rejectionReason`, `isActive`, `deletedAt`.

## A4. A15 in detail — `User.isActive`

**Schema:** `User.isActive Boolean @default(true)`. Migration `20260920000000_user_is_active` adds the column and converts existing rows: a `deletedAt` row with a matching `USER_DEACTIVATED` audit entry (and no later `USER_REACTIVATED`) becomes `isActive=false, deletedAt=NULL`; everything else with `deletedAt` is an owner deletion and stays deleted. On the dev DB this correctly moved `joe@test.com` (admin-deactivated) and left `shopper@test.com` (self-deleted) alone.

**Behaviour:**

| Case | Before | After |
|---|---|---|
| Suspended user, correct password → `POST /auth/login` | 401 INVALID_CREDENTIALS | **403 ACCOUNT_DEACTIVATED** "Your account has been deactivated. Contact support." — checked *after* the password so it reveals nothing to a guesser |
| Suspended user, wrong password | 401 INVALID_CREDENTIALS | unchanged |
| Suspended user's existing access token / refresh token | 401 | 401 INVALID_ACCESS_TOKEN / 403 ACCOUNT_DEACTIVATED on refresh |
| Owner-deleted user logs in | 401 INVALID_CREDENTIALS | unchanged — deleted means gone |
| Admin deactivates/reactivates an owner-deleted account | 204 / silently resurrected | **400 USER_DELETED** |
| Admin deactivates self | 400 CANNOT_DEACTIVATE_SELF | unchanged |
| Already suspended → deactivate again / already active → reactivate | 204 no-op, no audit row | unchanged (admin spec §4.4) |
| `GET /users/me`, `GET /admin/users`, `GET /admin/users/:id` | — | new `isActive` field |
| `GET /admin/overview` per-role counts | active = `deletedAt IS NULL` | active = not deleted **and** `isActive` |

Files: `prisma/schema.prisma`, the migration, `users.repository.ts` (`deactivate()` new, `reactivate()` flips `isActive`), `users.service.ts`, `dto/user-profile-response.dto.ts`, `auth.service.ts` (login + refresh), `auth.repository.ts` (`findAuthenticatedUserById` requires `isActive`), both unit specs. Verified over HTTP against the running server: all nine cases above returned the listed codes.

Spec impact: `users-module-spec.md` §3 ("does NOT delete related records") is now literally true for deactivate; `admin-module-spec.md` §4.4 and `web-dashboard-endpoints.md` §6.2 should mention `isActive` and the two new codes. Not yet edited.

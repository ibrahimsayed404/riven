## Why this exists

Riven needs to take real payments without Paymob for now (manual InstaPay / wallet transfers reviewed by an admin, and cash on delivery), while keeping Paymob working for later. The business is also moving to Riven holding vendor stock, shipping through couriers, collecting COD cash and settling with vendors, with a 6 % markup on vendor rates, location-based delivery fees and a vendor portal with monthly statements. A read-only audit of the current code found that none of this can be added safely on today's foundations: there is one stock column written in conflicting ways, one order status that mixes payment and delivery, payments that can be lost to a log line, and no ledger. These documents define the target design, the safety rules, the migration path and the decisions that must be made first.

Each phase: its blocking decisions approved → spec section reviewed → staged diff review (repository/service → controllers/DTOs → tests) → phase report with raw test output (`10` §3). Commits and pushes are the maintainer's.

Vendor-portal reads ship inside each phase for the data that phase creates (`vendor-module-spec3.md` §4).

**Production launch.** Real customer orders in production only after **every phase 0–7 has exited** (`10` §5) and the **production readiness gate PRG-01–PRG-14** passes (`10` §6). Working endpoints alone never qualify. *(Corrected 2026-10-25: an earlier version suggested first real orders at the end of Phase 4; Youssef's 2026-10-25 brief requires all phases — C22; the business acceptance of that timeline is BD-33, pending Ibrahim.)* Within that: COD stays disabled in production until Phase 5 exits (COU-01); returns after delivery stay disabled until BD-04 and FD-19 are approved (RET-02); PAYMOB stays disabled until a payment-reconciliation executor exists (TD-13, R-D4). "Phase 0 go-live" means deploying the hardened code, not opening commerce.

If Ibrahim rejects BD-15 (allows selling vendor-premises stock before intake), the order becomes 0 → 3 → 4 → 1 → 2 …, and vendor-premises stock is sellable through `warehouses.sellable`.

## What did not change

Paymob stays — **deferred, not rejected** (TD-21, 2026-10-27): disabled in production now, implemented and activated later through the PAYMOB activation milestone. The route, HMAC checks, intention flow, response fields and existing tests are preserved; the new payment model sits underneath and the old `paymob*` columns become a projection written in the same transaction (`06` §4). Shopper-facing order statuses keep their six values (`03` §13); vendor-facing statuses are a separate projection (`03` §14).
